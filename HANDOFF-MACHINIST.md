# MACHINIST Handoff — CAST Migration

**Date:** 2026-09-01
**Objective:** Migrate JAM/KANJUT/CIUM off the centralized JAM cmake toolchain
(`configure_app`/`AppBuilder.cmake`/`PluginBuilder.cmake`) onto CAST — a self-hosted
markdown-table-driven codegen tool (`~/Documents/Poems/dev/cast/`) that generates a
fully self-sufficient `CMakeLists.txt` per project, Projucer-equivalent, with zero
coupling back to JAM's cmake helpers.

**5-phase roster, ARCHITECT-approved:**
1. Build/sign/install CAST's own binary — **DONE**
2. Self-host CAST's own `CMakeLists.txt` via CAST — **BLOCKED, see below**
3. `eve` as the plugin-fence baseline — not started
4. Wire nvim's `build-debug.sh` to invoke `cast` — not started
5. Roll out to KANJUT/CIUM — not started

## Where we are right now

Phase 2's CAST-generated `cast/CMakeLists.txt` **configures cleanly** but **fails to
build** — not a CAST/template bug, a real pre-existing defect surfaced in JAM's own
framework headers once a truly headless (no GUI modules) consumer exercises them for
the first time. CAST is the first-ever headless-only JAM consumer; every prior
JAM/KANJUT project links `juce_gui_basics` for real GUI work, so this defect was
always latent and never triggered.

### Fixed already (this session)

- **`jam/jam_markdown/jam_markdown.h`** — removed `juce_graphics`/`juce_gui_basics`
  from `dependencies:` (confirmed dead: zero references to any GUI type anywhere in
  the module's actual `.cpp`/`.h` files). Guarded `#include <hb.h>` behind
  `#if JUCE_MODULE_AVAILABLE_juce_graphics`.
- **`jam/jam_markdown/document/jam_MarkdownDocument.cpp`** — guarded
  `isHarfBuzzSpaceSeparator`/`isHarfBuzzPunctuationOrSymbol` (and their callers
  `isUnicodeWhitespace`/`isUnicodePunctuation`) behind the same macro, with an
  ASCII-only fallback path when HarfBuzz isn't available. `hb_unicode_general_category`
  is genuinely used for CommonMark-spec Unicode whitespace/punctuation
  classification — real parsing-correctness code, not rendering — so this needed a
  fallback, not a silent removal.

### Found, NOT yet fixed — the current blocker

- **`jam/jam_core/jam_core.h:65,69,78`** — same disease, one level deeper.
  Unconditionally includes `juce_gui_basics`, `juce_gui_extra`, and
  `juce_audio_processors`, none of which are declared in its own `dependencies:`
  (`jam_core.h:10-14` only lists `juce_core, juce_data_structures, juce_events,
  juce_graphics`). Every JAM/KANJUT/CIUM project depends on `jam_core` — this is the
  framework's single most foundational module, so the fix here is higher-blast-radius
  than the `jam_markdown` one. **Next step: strip the three undeclared dependencies
  from `jam_core.h`'s metadata, guard the three `#include` lines behind
  `#if JUCE_MODULE_AVAILABLE_<module>`, then audit every file inside `jam_core/` for
  actual usage of GUI/audio-processor types needing the same guard** (mirror the
  `jam_markdown` pattern exactly).
- **`jam/generated/jam_Bimaps.h`'s `ColourIdMap` struct** — a JUCE-colour-ID-to-CSS
  map (`jam/cast/CAST.md:867-879`), generated by JAM's own separate CAST pipeline
  (`jam/cast/code.cast` + `jam/cast/CAST.md` — distinct from `cast`-the-tool's own
  templates). Its only real consumer in the whole framework is
  `jam/jam_style/style_manager/jam_StyleManager.cpp` (a module CAST never links), so
  guarding it costs nothing for real GUI consumers. **Blocked on an RFC, not yet
  actioned** — see below.

### RFC written, awaiting COUNSELOR

**`~/Documents/Poems/dev/jam/RFC-macro-scope-shape.md`** — `code.cast`'s
`namespace`/`struct` shapes each have exactly one `:::macro:::` slot (opening only,
e.g. for `#pragma once`); there's no matching closing slot, so an `#if ... #endif`
wrapper can't be expressed around a struct/namespace body today. Proposes a new,
independent **scope shape** (name TBD, needs NAMES.md Rule -1 ratification) — an
`#if`/`#endif` wrapper with its own `:::list:::`, composable around existing shapes
without modifying their arity. `ColourIdMap`'s manifest row would nest the existing
`@code:bimap` shape inside this new wrapper. Flagged but unresolved: `code.cast`
is already a de facto shared codegen library (`cast/cast/CAST.md`'s own index
references it directly, `@code | ../../jam/cast/code.cast`) — same
cross-framework-sharing question already resolved for `cmake.cast` (kept inside
`cast/cast/`, not any one framework's directory) may apply here too, but that's
explicitly out of scope for the RFC unless ARCHITECT wants it folded in.

**MACHINIST does not touch `jam_core.h`'s consumers or `code.cast` alone past the
already-completed `jam_markdown` fix** — the `jam_core.h` include/dependency strip is
build/toolchain-adjacent enough that MACHINIST did it directly (same as
`jam_markdown`), but the `code.cast` shape design is a C++-codegen-template
architecture decision that needs COUNSELOR's design pass per the RFC, then
delegation to Engineer.

## Next step, in order, once resolved

1. **COUNSELOR** designs the scope-shape grammar from the RFC, ratifies its name with
   ARCHITECT, delegates the `code.cast` + `jam/cast/CAST.md` wiring change to
   Engineer. Verify: `jam`'s own `cast` regenerates `jam_Bimaps.h` with `ColourIdMap`
   wrapped in `#if JUCE_MODULE_AVAILABLE_juce_gui_basics ... #endif`, and
   `jam_StyleManager.cpp` still compiles (GUI-linking projects still see
   `ColourIdMap` normally).
2. **MACHINIST** finishes `jam_core.h`'s own fix (dependencies + include guards +
   consumer audit), same shape as the already-completed `jam_markdown` fix.
3. **MACHINIST** re-runs CAST's full build from scratch:
   ```
   cd ~/Documents/Poems/dev/cast
   rm -rf Builds
   cmake -S . -B Builds/Ninja -G Ninja -DCMAKE_BUILD_TYPE=Release
   cmake --build Builds/Ninja -- -j"$(sysctl -n hw.logicalcpu)"
   ```
   Confirm: clean build, `POST_BUILD` codesign+notarize fires and succeeds
   (`codesign --verify`, notarization status Accepted) — matching Phase 1's already-
   proven result, this time from a CAST-generated `CMakeLists.txt` with zero JAM
   cmake-helper coupling.
4. **Phase 2 sign-off** — `cast/CMakeLists.txt.bak` (the pre-CAST original) can be
   discussed for removal once ARCHITECT confirms the generated file is trustworthy
   long-term; not deleted yet.
5. **Before Phase 3 (`eve`):** align `cast/build.sh`/`install.sh` — both currently
   hardcode a single `Builds/Ninja` directory (Release-only), inconsistent with the
   proven per-scheme-directory pattern (`Builds/Ninja/<Scheme>`) that
   `~/.config/nvim/scripts/build-debug.sh:23` already uses for every other
   JAM/KANJUT project. Not blocking for CAST itself (built once, not iterated via
   nvim's Debug/Release cycle), but `eve` *is* iterated that way — worth fixing
   first so Phase 3 doesn't inherit the inconsistency.
6. **Phase 3** — apply the `## juce module`/`## user module` universal schema (already
   proven in `cast/project-info.md`) to `eve`'s own `project-info.md`/`cmake.cast`;
   extract the shared fences into `cast/cast/cmake.cast` (already the agreed shared
   home, decided this session, to preserve JAM/KANJUT/CIUM decoupling); design the
   plugin-specific post-build/signing fields (potentially AAX-specific: PACE account,
   wcguid); resolve the Debug/Release generator-switch question — likely just reusing
   the same per-scheme-directory pattern, not a multi-config generator switch, per
   finding in step 5.
7. **Phase 4** — one-line change to `~/.config/nvim/scripts/build-debug.sh`: invoke
   `cast` (from the project's `cast/` dir) unconditionally near the top of the
   script, before the existing `if [ ! -f CMakeCache.txt ]` guard — not inside it.
   CAST's write-if-different means this is a cheap no-op when nothing changed, and
   CMake/Ninja's own reconfigure-on-`CMakeLists.txt`-mtime-change behavior handles
   picking up a regenerated file automatically. Nothing else in that script changes.
8. **Phase 5** — roll the same pattern out to KANJUT/CIUM-based projects.

## Minor open item, not blocking

`message(STATUS "${PROJECT_DESCRIPTION}")` (added this session, `cast/cast/cmake.cast`)
prints CAST's own ASCII banner at configure time as literal, unescaped UTF-8 —
proven working via manual `cmake -S -B` test. CMake separately emits
`Value of CMAKE_PROJECT_DESCRIPTION contained a newline; truncating` during its own
internal generate step — cosmetic (our own printed banner is already captured in full
beforehand), but if ARCHITECT wants a fully warning-free configure log, `description`
could be split into a short single-line official `project()` description plus the
multi-line banner text used only by the `message()` call, decoupling the two
concerns.
